目标：先验证真实 RGB-D 检测/定位，再验证一个伤员的“探索 → 接近 → 停车 → 模拟救援 → 恢复探索”。
当前没有真实坐下/趴下指令；本轮 COMPLETED 必须解释为 mock 完成。

## 3. T01：静止验证传感器、TF、地图（约15分钟）

先不启动任何自主探索器、键盘运动控制或运动桥接。

1. 按团队已验证方式启动相机，启用 aligned depth，确认真实 topic 名。
2. 已有 /utlidar/* 时不重复启动 go2_driver。
3. 启动单一机器人模型/静态 TF 来源（若环境尚未提供）；相机 TF 必须用该机实际标定。
4. 启动一种建图流程，不同时运行两套 retime/odom TF。

本地接收时间适配流程（只适用于已经核实的本地标定；此 launch 默认相机 TF 来自 seek）：

```bash
ros2 launch go2_bringup go2_mapping_pipeline.launch.py \
  database_path:=/rtab_map_data/rescue_test_20261111.db
```

这个组合已经含 retime_utlidar、相机 TF、相机重打戳、RTAB-Map。
不要再同时启动 go2_online.launch.py：它也会启动 retime_utlidar，造成重复 odom TF。
若需要 robot_state_publisher，可单独使用 go2_description 的机器人描述 launch，明确传 `use_sim_time:=false`（默认是true），并核对它与相机标定不会重复发布同一child frame。
如果旧环境已完整启动建图，保持原流程，不再启动这个组合。
比赛机使用 competition mapping launch 和该机标定，detector 三个输入也要换成实际原始 topic；
不要混用本地重打戳 RGB 和原始深度。

```bash
ros2 topic list
ros2 topic info /lumen/retimed/rgb -v
ros2 topic info /lumen/retimed/depth -v
ros2 topic info /lumen/retimed/rgb_info -v
ros2 topic hz /utlidar/robot_odom_retimed
ros2 topic echo /lumen/retimed/rgb --field header --once --qos-reliability best_effort
ros2 topic echo /lumen/retimed/depth --field header --once --qos-reliability best_effort
```

查看 rgb_info 的尺寸、K、D，以及 depth encoding。RGB、aligned depth、CameraInfo 应对应同一 RGB optical frame。
将下面 camera_color_optical_frame 换为图像 header 中的真实 frame：

```bash
ros2 run tf2_ros tf2_echo map base_link
ros2 run tf2_ros tf2_echo map camera_color_optical_frame
```

通过：RGB/深度持续更新；深度为16UC1或32FC1；内参对应；map TF有效；地图与现场方向一致。
停止条件：没有图像、深度未对齐、TF 缺失/重复、地图明显跳变，先排障，不能进入运动测试。

## 4. T02：静止 detector 与地图定位（约15–20分钟）

启动只观测的模式：

```bash
ros2 launch sar_target_mapping detector_mapping.launch.py \
  output_file:=/results/t02_observations.json
```

此时不启动 rescue_mission。用 RViz（在已配置显示的机器上）查看 map 和 /sar_integration/targets/markers。
另一个终端：

```bash
ros2 topic echo /sar_detector_integrated/status
ros2 topic echo /sar_integration/status
```

依次执行：

| 项目 | 操作 | 观察/建议通过条件 |
|---|---|---|
| 空场 | 30秒无道具 | 有处理帧；无持续虚假 mannequin 地图记录；偶发误报也要记录 |
| 已知伤员 | 在相机前约2m摆伤员，保持10–20秒 | raw → confirmed → localized 顺序出现 |
| 位置误差 | 记录地面参考位置，与RViz map标记比较；换约1.5m、2.5m、3m位置 | 首轮建议平面误差≤0.3m；这是待验证门槛，不是代码保证 |
| 重复观测 | 同一伤员连续观察 | unique_targets 基本稳定，不持续新增 |
| 移出视野 | 移走伤员/遮挡 | 当前确认检测应清空，历史地图记录可以保留，这是预期行为 |
| 类别 | 分别摆cone、first_aid | 类别正确，之后不能被任务协调器当伤员救援 |

静止定位测的是物体可见表面估计，人工 ground truth 定义要一致，别用人体中心与表面直接比较。
定位误差/假目标偏大时，不进入自动接近；保存短 bag 排查。

负载要求：记录 infer_ms、frames、skipped、CPU/GPU/内存。CPU 模式先关调试图，默认就是关闭。
推理和排队总延迟应留在深度缓存及2s观测时效内；30Hz深度缓存约1s，建议观察实际端到端延迟。
必要时运行宿主机 top 或 Jetson 的 tegrastats（若已安装）；不要在测试中盲目替换GPU依赖。

## 5. T03：确认 Nav 基线（约15分钟）

先 Ctrl+C 关闭 T02 detector_mapping（避免下一步重复 detector/mapper）。
机器人保持静止，先运行原 Nav、运动关闭：

```bash
ros2 launch go2_bringup go2_navigation_rtabmap.launch.py enable_motion:=false
```

检查 planner/controller/bt navigator/collision_monitor 等节点处于 active、两个 action 可用：

```bash
ros2 action list -t
ros2 lifecycle get /planner_server
ros2 lifecycle get /controller_server
ros2 lifecycle get /bt_navigator
ros2 lifecycle get /collision_monitor
ros2 topic info /global_costmap/costmap -v
ros2 topic info /global_costmap/costmap_updates -v
```

若旧倒下问题仍未解决，这一阶段止于无运动接口检查。
确认现有 Nav 单独运动稳定后，才停掉这一个 Nav launch，再以低桥接限速重启；不能并行启动两个：

```bash
ros2 launch go2_bringup go2_navigation_rtabmap.launch.py \
  enable_motion:=true bridge_max_vx:=0.10 bridge_max_vy:=0.05 bridge_max_wz:=0.20
```

此处是真运动启用点。数字是桥接输出限幅，不会自动重调控制器；如Nav抖动或无法进展，停止诊断，不直接提速。
在没有新任务协调器/探索器运行时，由操作员用已验证的方式发一个约0.5–1m开阔处目标。
通过：平稳起步、到达和停止，无倒下、命令竞争、明显定位漂移；验证手柄停止可用。
然后取消/结束该手动任务，之后不要再用RViz发目标。

## 7. T05：一个伤员完整闭环（约20分钟）

先保证T03通过，运动桥接为低限速、当前无外部导航目标。
伤员放在开阔处，距机器人约2–3m，周围留足1m接近环及机器人空间，避免挡住相机。
每轮正式启用前准备好状态观察、bag和物理停止。

```bash
ros2 service call /sar_rescue/set_enabled std_srvs/srv/SetBool '{data: true}'
```

通过响应必须success=true；失败就按message排查，不反复启用绕过检查。
预期顺序：

```text
EXPLORING → PAUSING_EXPLORATION → SELECTING_APPROACH
→ APPROACHING → VERIFYING_TARGET → RESCUING → EXPLORING
目标记录最终为 COMPLETED，completion_mode=mock
```

检查：

- 机器人朝伤员附近接近点行走，不是撞向伤员地图坐标。
- 暂停后不被探索目标抢走；一次最多执行一个导航任务。
- 到达后目标仍在相机视野；必须有到达后的新定位观测和持续1s静止。
- 模拟动作约2s，不出现坐下/趴下/站起指令。
- 完成后会立即恢复探索，不能把“已完成”理解为机器人此后一直不动。
  第一次看到恢复探索即可调用禁用服务，等待DISABLED并确认停稳。

```bash
ros2 service call /sar_rescue/set_enabled std_srvs/srv/SetBool '{data: false}'
```

建议3次独立单目标试验，分别用新的 ledger 文件和 mission_id；记录每次结果，不用一次成功代表稳定。
同一轮重复识别/重启测试则保留相同地图、mission_id、ledger，不能清空完成记录。
如果第一轮目标一开始已确认，会很快切换接近；后续可让机器人先探索一小段再看到目标，以验证真正的中途抢占。

## 8. T06：重复目标、重启与多目标（有时间再做，约20分钟）

| 测试 | 条件与操作 | 通过条件 |
|---|---|---|
| 已完成目标再出现 | 同一地图/ledger，保持伤员原位，重新启用 | 不再次救援该目标 |
| 进程重启 | 先禁用等DISABLED，再重启组合launch；建图/定位保持，ledger与mission_id不变 | 仍从DISABLED开始，COMPLETED保留，再出现不重复处理 |
| 两个伤员 | 两目标间距明显大于0.6m去重半径，空间足够 | 一次一个，完成第一个后选择第二个；记录2个不同编号 |
| 无可达目标 | 只在机器人停稳且任务禁用时布置静态阻挡，再启用 | 无接近点/路径时DEFERRED，机器人不强行靠近 |

机器人重新建图导致map原点改变时，不用旧ledger做重启去重测试；那属于不同坐标系，需要新任务记录。

## 9. T07：失败路径（静止或运动关闭时验证）

- 静止禁用状态下，暂停 detector，查看状态计数和新鲜度；不要以历史地图标记推断detector还活着。
- 验证阶段缺少新的伤员观测，应超时暂缓，不应标COMPLETED。
- TF/里程计/代价地图失效，启用检查应失败；运行中失效会FAULT。
- mock结果不返回，应FAULT而非标完成。
- 不在首次真机运动中直接拔相机、kill建图/协调器或制造取消无响应；这些先用回放/隔离测试。
  协调器死掉不保证Nav2停下；心跳只停止探索器提议。

## 10. 停止与异常处理

正常停止：set_enabled false → 观察DISABLED → 物理确认停稳 → 关闭集成，再关Nav/建图。
出现异常运动、姿态不稳或接近距离异常时，观察员立即使用已验证的物理停止方式。
禁用服务不是物理急停；不要只Ctrl+C协调器假定机器人会停。
FAULT不自动恢复；记录reason、取消状态和日志，确认物理停止后再诊断重启。
任何倒下都停止本轮运动测试，检查机器人并回退到稳定Nav基线。
